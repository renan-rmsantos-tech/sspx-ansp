# ADR-006: Database aggregation for geographic reports

## Status

Accepted

## Date

2026-10-13

## Context

The reports need two distinct geographic counts and shared filters without exposing personal records to the chart interface.

## Decision

Aggregate both report series in Postgres after applying the same period and contribution-frequency filters. Return category labels, counts, and a total to an administrator-only server action. Include explicit unknown residence and none or unknown chapel categories.

## Alternatives Considered

### Alternative 1: Group all rows in application memory

- **Description**: Fetch all donor registrations and count in the server process.
- **Pros**: Simple TypeScript grouping.
- **Cons**: Transfers personal rows unnecessarily and scales with row count.
- **Why rejected**: SQL aggregation is smaller and limits data exposure.

### Alternative 2: Group in the browser

- **Description**: Send donor rows to a client component.
- **Pros**: Interactive filters without server requests.
- **Cons**: Exposes addresses, CPF, and email to the report client.
- **Why rejected**: Conflicts with the PRD's aggregate privacy boundary.

## Consequences

### Positive

- The report payload contains counts only and remains efficient as registrations grow.

### Negative

- Query tests need a real Postgres integration path to verify grouped totals.

### Risks

- Different null and special `none` values can distort totals. Map them explicitly and assert that each series sums to the selected population.

## Implementation Notes

Authorize every report read with `requireAdmin()`. Filter by `donor_pledges.created_at` and `frequencia` using one normalized filter contract.
