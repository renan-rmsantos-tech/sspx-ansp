# ADR-005: Database reservation for welcome email sends

## Status

Accepted

## Date

2026-10-13

## Context

Automatic registration sends and administrator retries can race. The current sent timestamp is written only after the email provider accepts the message, so simultaneous calls can send duplicates.

## Decision

Use an atomic, time-limited reservation on the donor row before sending. Only the caller that acquires the reservation sends. Clear it after a failed attempt; mark `welcome_email_sent_at` only after provider acceptance. An expired reservation can be acquired again. Both automatic and manual paths use the same service.

## Alternatives Considered

### Alternative 1: Persistent queue

- **Description**: Enqueue messages for a separate worker.
- **Pros**: More retry control.
- **Cons**: Adds worker lifecycle and operational complexity.
- **Why rejected**: The current volume and PRD do not justify it.

### Alternative 2: Client-side button lock

- **Description**: Disable the send button during requests.
- **Pros**: Small UI change.
- **Cons**: Does not coordinate browsers or automatic registration sends.
- **Why rejected**: It cannot prevent server-side races.

## Consequences

### Positive

- Concurrent calls for one registration cannot both begin an avoidable send.

### Negative

- A crash after provider acceptance but before recording the timestamp can still permit a later duplicate; the provider request lacks a transaction with Postgres.

### Risks

- Expiry must exceed the provider request timeout and still allow eventual recovery. Return a clear in-progress result while the reservation is active.

## Implementation Notes

Do not hold a database transaction open during the network call. Use conditional updates and a reservation token to ensure only the owner clears or completes it.
