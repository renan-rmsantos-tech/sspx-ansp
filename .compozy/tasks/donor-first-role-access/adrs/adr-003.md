# ADR-003: Extend the existing staff account model and centralize authorization

## Status

Accepted

## Date

2026-08-31

## Context

`admin_users` is the existing source of authenticated staff accounts and is already referenced by application decisions. Sessions currently carry only user identity, `proxy.ts` checks only whether a session exists, and every Server Action uses the same binary authentication check. The new Secretariat profile must be denied sensitive capabilities and deactivated accounts must lose access even when an old cookie remains valid.

## Decision

Add a required `role` value (`admin` or `secretaria`) and an `ativo` flag to `admin_users`. Backfill every existing account as an active Administrator before enforcing the new constraints. Keep both profiles under `/admin`.

Treat the session as an identity hint only. Every protected page and Server Action must load the current account and confirm that it remains active. Central authorization helpers expose role and capability checks; restricted Server Actions require Administrator capability explicitly. Secretariat reads use dedicated projections that never select prohibited fields. `proxy.ts` remains a coarse unauthenticated redirect, not the authorization boundary. The development bypass resolves to an active Administrator and remains unavailable in production.

## Alternatives Considered

### Alternative 1: Separate Secretariat account table

- **Description**: Keep `admin_users` unchanged and create an independent account table and authentication path for Secretariat staff.
- **Pros**: Strong conceptual separation between profiles.
- **Cons**: Duplicates authentication, password, session, and account-lifecycle behavior and complicates references to staff authors.
- **Why rejected**: Both profiles are staff using the same panel and identity lifecycle; one account model is simpler and preserves current references.

### Alternative 2: Store the role only in the session

- **Description**: Resolve role at login and trust it until the session expires.
- **Pros**: Avoids an account lookup on protected operations.
- **Cons**: Role changes and deactivation do not take effect immediately, and authorization state can become stale.
- **Why rejected**: Immediate revocation is required for sensitive family data.

## Consequences

### Positive

- Existing staff and decision records remain valid.
- One account lifecycle supports both profiles.
- Authorization rules are reusable and reviewable.
- Account deactivation takes effect on the next protected request.
- Restricted data never needs to reach Secretariat client components.

### Negative

- Protected reads and writes perform an account lookup.
- Existing actions must be classified and migrated to explicit capability checks.

### Risks

- A missed action could retain broad access; maintain a complete capability matrix and deny unspecified Secretariat operations.
- A UI-only restriction could leak data in payloads; use server-side projections and action checks.

## Implementation Notes

- Use text columns with database checks, consistent with the current schema conventions.
- Add the backfill before `NOT NULL` and role checks become effective.
- Keep `userId` and `email` in the iron-session payload; do not make the cookie authoritative for role or activity.
- Split helpers into authenticated-user resolution plus `requireAdmin()` or `requireCapability()` checks.
