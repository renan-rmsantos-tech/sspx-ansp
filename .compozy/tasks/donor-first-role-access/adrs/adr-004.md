# ADR-004: Store Secretariat observations as append-only records

## Status

Accepted

## Date

2026-08-31

## Context

Applications currently have no operational note model. The approved product behavior requires a dated history whose author is identifiable, which Secretariat staff can append and Administrators can read. Notes must not be edited into a single mutable blob or included in generated family documents.

## Decision

Create an `application_observations` table with an immutable row for each entry. Each row contains an ID, application reference, author account reference, body, and creation timestamp. Order entries chronologically and index the application and timestamp access path.

Expose only creation and read operations. Secretariat users can append and read observations for applications available to them; Administrators can read the history. Do not add update or delete operations and do not join observations into any PDF render input.

## Alternatives Considered

### Alternative 1: Structured list inside the application row

- **Description**: Store the history as a JSON list in `applications`.
- **Pros**: Avoids a new relational table.
- **Cons**: Rewrites the full list for every entry, weakens author integrity, complicates indexing, and creates concurrent-update risk.
- **Why rejected**: Observations are independent authored events and fit an append-only relation.

### Alternative 2: One mutable text field

- **Description**: Store the latest notes in a single application column.
- **Pros**: Smallest schema change.
- **Cons**: Loses authorship and chronology and allows accidental overwrites.
- **Why rejected**: It cannot satisfy the approved history requirement.

## Consequences

### Positive

- Authorship and chronology are explicit.
- Concurrent additions do not overwrite existing notes.
- PDF isolation is easy to audit.

### Negative

- The application detail flow needs a separate read and append operation.
- Notes grow without in-product deletion.

### Risks

- Staff may enter unnecessary sensitive data; constrain length and show operational-writing guidance.
- Orphaned authors could harm auditability; deactivate accounts rather than deleting them.

## Implementation Notes

- Use foreign keys to `applications` and `admin_users`.
- Reject empty or whitespace-only bodies and define a conservative maximum length.
- Return author display identity and timestamp from the server projection.
