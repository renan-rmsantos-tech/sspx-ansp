# ADR-005: Persist immutable versions of issued final documents

## Status

Accepted

## Date

2026-08-31

## Context

Decision and contract exports currently render a PDF into memory and return base64 without recording issuance. The Secretariat must download only documents an Administrator has actually issued, while reissuance must preserve prior versions for administrative traceability. Applicant uploads already use protected storage but are a different document category.

## Decision

Persist every Administrator issuance or reissuance as an immutable `issued_documents` row and a PDF stored in a dedicated issued-document namespace. Record the application, kind (`decision` or `contract`), version, storage metadata, issuing Administrator, and issuance timestamp. Determine the current version by the highest version for each application and kind; never overwrite or mutate an earlier version.

Administrator issuance renders the PDF, stores it, and records the immutable version. Secretariat list and download operations accept an issued-document ID, resolve it server-side, confirm the caller's capability, and issue a short-lived download ticket. They never accept an arbitrary storage path. Secretariat projections return only the latest issued decision and, for approved applications, the latest issued contract. Administrator views may expose version history.

## Alternatives Considered

### Alternative 1: Replace the current file on reissuance

- **Description**: Keep one row and one path per document kind and overwrite it.
- **Pros**: Less storage and simpler latest-document lookup.
- **Cons**: Destroys the prior issued artifact and weakens traceability.
- **Why rejected**: The user selected immutable issuance history.

### Alternative 2: Regenerate on Secretariat download

- **Description**: Continue generating PDFs from current application and template data whenever requested.
- **Pros**: No additional file persistence.
- **Cons**: Cannot prove prior issuance and may silently change the content after templates or data change.
- **Why rejected**: It contradicts the requirement to expose only documents already issued by an Administrator.

## Consequences

### Positive

- Issuance becomes explicit and auditable.
- Secretariat downloads reproduce the exact issued artifact.
- Reissuance does not erase history.
- Applicant evidence and final documents remain segregated.

### Negative

- PDF storage grows with every version.
- File and database writes require failure compensation to avoid orphaned artifacts or rows.

### Risks

- A partially failed issuance could leave inconsistent state; stage the file and clean up on database failure.
- Arbitrary-path downloads could bypass categorization; authorize by persisted document ID before creating tickets.
- Concurrent reissuance could duplicate version numbers; enforce uniqueness and serialize version allocation through the database.

## Implementation Notes

- Add a unique constraint on `(application_id, kind, version)` and an index supporting latest-version reads.
- Keep applicant `documents` unchanged.
- Reuse the storage driver and download-ticket mechanism after authorization.
- Preserve current PDF renderers and return the newly persisted artifact to the Administrator after successful issuance.
