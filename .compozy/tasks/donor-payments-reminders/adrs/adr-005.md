# ADR-005: Attach reminder receipts to early occurrence records

## Status

Accepted

## Date

2026-10-26

## Context

The operator requires every monthly payment reminder to contain a link for uploading that occurrence's required Pix receipt without login. The prior sequence created the payment ledger only in phase 3, after reminders were already live in phase 2. A phase-2 upload needs a durable pledge/competence target without implying bank receipt or depending on the later conference release. ADR-007 adds the required-receipt state and reminder suppression rule.

## Decision

Create a minimal `donor_payment_ledger` and monthly occurrence materialization in phase 2. Each `(pledge_id, competencia)` row begins with a required receipt pending and holds one active receipt after upload. Each reminder carries an expiring HMAC bearer link scoped to that pledge and competence, signed with a derived key distinct from existing upload/download tickets. A public page shows only first name, month, and amount and accepts one image/PDF up to 10 MB. A valid later upload replaces the active receipt while the link is valid, including after a bank credit was confirmed without changing that bank state; new evidence after “Não identificado” returns the row to pending conference. The page never marks a payment received. In phase 3, extend the same rows with bank conference fields, backfill one-time pledges, and show the monthly receipt as evidence awaiting conference.

## Alternatives Considered

### Alternative 1: Keep the ledger in phase 3 and store phase-2 receipts by reminder send row

- **Pros**: No earlier ledger migration.
- **Cons**: Two sends for one payment need extra reconciliation; the phase-2 receipt has no canonical expected-payment row and phase 3 must migrate it.
- **Why rejected**: It risks duplicate or orphaned evidence and complicates independently releasable phases.

### Alternative 2: Delay receipt upload until phase 3

- **Pros**: Smaller phase 2.
- **Cons**: Phase-2 reminders cannot satisfy the required link and upload behavior.
- **Why rejected**: It fails the operator's final requirement.

## Consequences

### Positive

- Both reminder kinds point to one durable payment occurrence and one active receipt; an uploaded receipt suppresses remaining reminders for that occurrence under ADR-007.
- Phase 2 can release reminders and receipt intake together; phase 3 can add conference without migrating receipt ownership.
- A receipt remains evidence only; bank-confirmed values continue to require administrator action.

### Negative

- Phase 2 now includes an additional migration, private storage workflow, and public bearer-link surface.
- The single-container in-memory throttle must be replaced by shared rate limiting before deploying multiple app replicas.

### Risks

- Forwarded or leaked links remain usable until expiry. Limit page data, sign and scope the link, set no-store/no-referrer headers, throttle requests, redact URLs from logs, and never expose a public file download.
- File/database updates can fail between steps. Use unique versioned paths, conditional row updates, and cleanup/compensation so replacement never silently loses the active receipt.

## Implementation Notes

Follow TechSpec “Per-Occurrence Receipt Link and Upload.” Phase-2 rows contain only expected-payment and receipt fields; phase-3 migration adds credit/status/confirmer fields. Keep `pending/{uuid}/...` staging and private `donors/{pledge_id}/payments/{competencia}/...` final paths.
