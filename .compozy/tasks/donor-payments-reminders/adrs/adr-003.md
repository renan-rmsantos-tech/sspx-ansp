# ADR-003: Use a daily opted-in email job with per-occurrence reservations

## Status

Accepted

## Date

2026-10-26

## Context

There is no scheduler in the app, while the droplet already runs operational cron commands. The existing welcome-email path uses Resend and a short database reservation. Reminders need an independent record for each pledge, due month, and 10-day or 5-day kind.

## Decision

Run one npm script inside the application container each day from droplet cron. Select only monthly, email-opted-in, active occurrences whose due date is exactly 10 or 5 local calendar days away. Record a unique row for `(pledge_id, competencia, kind)` and use a short lease/reservation before calling Resend. Store acceptance and a sanitized failure state, require review of uncertain provider outcomes, allow administrator retry only after definite failure, and never resend a recorded accepted message. Reuse the institutional email rendering and document header. Once the ledger exists, skip occurrences with a bank-confirmed credit.

## Alternatives Considered

### Alternative 1: Add a separate queue and worker service

- **Pros**: Flexible scheduling and retry infrastructure.
- **Cons**: New deployment and operations surface for two daily emails per occurrence.
- **Why rejected**: The droplet cron and current app are sufficient for this workload.

### Alternative 2: Send reminders from web requests

- **Pros**: No cron setup.
- **Cons**: Delivery depends on site traffic and request timing.
- **Why rejected**: The schedule would be unreliable.

## Consequences

### Positive

- Each scheduled send is visible and safe to rerun under normal concurrent or repeated execution.
- The existing email configuration and header remain the authority.

### Negative

- Cron must be installed and monitored on the droplet.
- A run missed entirely on its scheduled day does not produce a late message.

### Risks

- Provider acceptance and database commit cannot be atomic. Use a stable Resend idempotency key and a frozen payload to narrow the crash window; the provider currently documents a 24-hour key lifetime. Record and surface any uncertainty rather than claiming delivery.

## Implementation Notes

Keep provider calls outside an open database transaction. The unique key and lease owner coordinate workers. A test-send must not create a reminder row.
